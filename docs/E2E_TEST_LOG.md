## Fix pass A (14 Oct, offline: no live model, local database only)

Fixed: L1, L2, L3, L4, L7, #5, #8, #12, #13, #18 and C1 (the Status cells above carry the commit SHAs). The live AI run (C3) is round 2.

**Root causes found**

- **L1 / L7 (1 student became 27, then 53).** The audit rows of the logged plan show two separate faults. (1) The revise form re-sends the current student list on every save, and the planner only treated a list as the mentor's if it differed from the saved one, so an unchanged one-student selection was open to replacement: a request that said "my mentees ... attendance below the policy threshold" resolved to every mentee matching the model's criteria (1 became 27). (2) The model added criteria the request never stated and they differed between saves: one save used a semester window 4 to 8 plus a mark cut-off of 60, the next used semester 4 and up only, so the same request matched 27 and then 53 students. The server took whatever criteria the model returned. The planner never saw the selection either (only a count), hence "Which single student did you select...?".
- **#13 (corrupted feedback text).** The revision box was pre-filled with the saved feedback, so a new answer was typed into the middle of the old text. Not a server merge fault.
- **#8.** The Core sent per-student risk (score, band, signals, evidence values) to the department head in the overview, the review queue and the plan export; the page note only hid the tab. Band averages over one student also exposed that student's score.
- **#12.** `planWithAgent`, `savePlan`, `lockPlan`, `executePlan` and `setReviewPaused` accepted the department head and governance roles; only the page hid the controls.

**What changed**

- Selection is authoritative and reaches the planner (count plus `stu-N` aliases). The planner may narrow it or ask a question; it never replaces or widens it. A request that describes a different or wider set is stored on the plan as a scope conflict and the plan is not ready until the mentor answers "Keep my N" or "Use the M from my request"; only that answer changes the scope. Numeric criteria must be grounded in the request text or an approved policy threshold, planner aliases use a request-derived salt, an unchanged re-save does not re-plan, and the student set is a pure function of selection, grounded criteria and data. The regex feedback-directive parser is removed, so free text cannot override typed scope.
- Notes accumulate one per line on the server; the box opens empty after every save; questions answered by a new note go to the planner as resolved and are filtered server-side.
- C1: no execution mode, no rule-based draft, no regex planner fallback. When no model answers, a review waits as "AI unavailable, retry" (job failed, not escalated, attempt not spent, reasons in `failure_diagnosis` and the `execution.stopped` audit row, sent requests still audited); a plan is not saved and the mentor is asked to retry (`planner.unavailable` audited). Retired rule-based drafts stay in the database, leave the active queue and sit under a collapsed read-only "Legacy drafts" section; the Core refuses to edit or decide them. Student 021's pending case is an AI-written draft and stays in the active queue, undecided. Provider chain: Groq, Gemini, then the local Qwen model.
- #8 / #12: only the assigned mentor sees risk figures and runs plan commands (Core and page). Department views get aggregates, with band averages suppressed under three students.

**Not changed (still open)**: #1, #2, #3, #4, #6, #7, #9 to #11, #14 to #17, #19 to #32, L5, L6, C2 to C5. The legacy support-event flow in `support-commands.ts` (`processAcademicEvent`) still has its own rule-based recommendation; the Streamlit app never calls it.
