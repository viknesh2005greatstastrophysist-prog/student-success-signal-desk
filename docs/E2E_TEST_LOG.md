## Fix pass A (14 Oct, offline: no live model, local database only)

Fixed: L1, L2, L3, L4, L7, #5, #8, #12, #13, #18 and C1 (the Status cells above carry the commit SHAs). The live AI run (C3) is round 2.

**Root causes found**

- **L1 / L7 (1 student became 27, then 53).** The audit rows of the logged plan show two separate faults. (1) The revise form re-sends the current student list on every save, and the planner only treated a list as the mentor's if it differed from the saved one, so an unchanged one-student selection was open to replacement: a request that said "my mentees ... attendance below the policy threshold" resolved to every mentee matching the model's criteria (1 became 27). (2) The model added criteria the request never stated and they differed between saves: one save used a semester window 4 to 8 plus a mark cut-off of 60, the next used semester 4 and up only, so the same request matched 27 and then 53 students. The server took whatever criteria the model returned. The planner never saw the selection either (only a count), hence "Which single student did you select...?".
- **#13 (corrupted feedback text).** The revision box was pre-filled with the saved feedback, so a new answer was typed into the middle of the old text. Not a server merge fault.
- **#8.** The Core sent per-student risk (score, band, signals, evidence values) to the department head in the overview, the review queue and the plan export; the page note only hid the tab. Band averages over one student also exposed that student's score.
- **#12.** `planWithAgent`, `savePlan`, `lockPlan`, `executePlan` and `setReviewPaused` accepted the department head and governance roles; only the page hid the controls.

**What changed**

- Selection is authoritative and reaches the planner (count plus `stu-N` aliases). The planner may narrow it or ask a question; it never replaces or widens it. A request that describes a different or wider set is stored on the plan as a scope conflict and the plan is not ready until the mentor answers "Keep my N" or "Use the M from my request"; only that answer changes the scope. Numeric criteria must be grounded in the request text or an approved policy threshold, planner aliases use a request-derived salt, an unchanged re-save does not re-plan, and the student set is a pure function of selection, grounded criteria and data. The regex feedback-directive parser is removed, so free text cannot override typed scope.
- Notes accumulate one per line on the server; the box opens empty after every save; questions answered by a new note go to the planner as resolved and are filtered server-side.
- C1: no execution mode, no rule-based draft, no regex planner fallback. When no model answers, a review waits as "AI unavailable, retry" (job failed, not escalated, attempt not spent, reasons in `failure_diagnosis` and the `execution.stopped` audit row, sent requests still audited); a plan is not saved and the mentor is asked to retry (`planner.unavailable` audited). Retired rule-based drafts stay in the database, leave the active queue and sit under a collapsed read-only "Legacy drafts" section; the Core refuses to edit or decide them. Student 021's pending case is an AI-written draft and stays in the active queue, undecided. Provider chain: Groq, Gemini, then the local Qwen model.
- #8 / #12: only the assigned mentor sees risk figures and runs plan commands (Core and page). Department views get aggregates, with band averages suppressed under three students.

**Not changed (still open)**: #1, #2, #3, #4, #6, #7, #9 to #11, #14 to #17, #19 to #32, L5, L6, C2 to C5. The legacy support-event flow in `support-commands.ts` (`processAcademicEvent`) still has its own rule-based recommendation; the Streamlit app never calls it.

## Fix pass B (14 Oct, offline: no live model, local database only)

Fixed: #1, #2, #3, #6, #7, #9, #10, #11, #14, #26, #30 (the Status cells above carry the commit SHAs). #29 is closed as source data. Not touched: the visual and layout items (#4, #15 to #17, #19 to #25, #27, #28, #31, #32, L5, L6), which wait for the redesign (C2), and #20 and #22, which are display polish.

**Root causes found**

- **#1, #2, #9 (112 vs 57 vs 329 vs 161).** Four different things were being counted under one word. The mentor and department overviews counted *jobs* whose status was `awaiting_faculty` (a job keeps that status after the mentor decides, so it never goes down: 329 jobs against 161 open cases); the Support reviews page counted *queue rows*, and the queue was one row per open case, so a student with several review cycles appeared several times; and the "Flagged students" figure came from risk rows, one per student and cycle. Now one rule in `chapter11/awaiting.ts`: an open case with an active AI draft, the newest draft per student, earlier drafts shown as history under that student, legacy rule-based drafts never counted, and an open case dropped when the same student has a later case that was already decided. The review queue and both overview counts call it. Against the local data: mentors 52, 51 and 51, department head 154 (it was 112 / 57 / 329 / 161); queue length, queue count and overview count are equal for every role (asserted in the DB suite and in `verify_chapter11_trends.py`).
- **#6 (Evaluated 221, Flagged 113 for 107 students).** Risk rows are student x review cycle and were counted as students. The Core now marks one `latest` row per student (the newest cycle that evaluated them); the cards read "Students evaluated" and "Students flagged", the table shows one row per student ("All assigned cycles") or that cycle's rows, and the page header "Flagged students" uses the same rows. mentor1 now reads 107 students.
- **#7.** The page read `course_count`; the Core returns `active_registrations` for students (`course_count` belongs to the faculty list). A field-name mismatch, not a missing join.
- **#3.** The badge looked only at `valid`. It now says "Checks not recorded for this version" when none of the four acceptance checks is recorded, "Passed the N recorded of 4 checks" when only some are, and "Passed every check" only when all four are recorded and true.
- **#10.** The header counted every escalated job (2); the Evaluation tab counted only escalated jobs that had a validation record (1), because one escalated job stopped before validation. Both now read `metrics.totals`. The "100% pass" was `round(99.7)`: one failing run out of about 330 rounded up. The percentage no longer reaches 100% unless every evaluated draft passed, and the help text gives "N of M".
- **#11 (ten identical Queued / Collect rows).** Not stuck leases. The 20 queued jobs had never been claimed (`attempts` 0, no lease token, no support case): they belong to 20 locked plans that nothing ever ran. 19 are the plan that `verify_chapter11_planning.py` creates on every run (it locks the plan and stops before execution by design) and one is the "Stale refresh acceptance" plan. The Phase 0.8 sweep only reclaims `running` jobs whose lease expired, so it correctly ignored them; a locked plan waits until a mentor presses Run. The display counted them as "recorded runs" and listed them first. ## Rework: hosted speed (15 Oct, worker 4: final verification)

The hosted app (https://aura-college-workspace.streamlit.app) is public: the first 303 to `share.streamlit.io/-/auth` is only Streamlit's cookie bootstrap, and a browser that follows it lands on the app. It already served the Apple sign-in (blue Continue) before this pass, so it was running the latest design commit. **Cause.** The hosted app runs in the United States (Streamlit Community Cloud: community reports say Google servers in the USA; consistent with a 0.43 s page switch that makes no database call, against 0.10 s locally, which is about one 0.3 s round trip between India and the US). The Neon database is in `ap-southeast-1` (Singapore). Between them a database round trip costs roughly 0.2 to 0.25 s, and an engine call makes 12 to 25 of them one after another (each transaction alone cost five: BEGIN, search path, lock, the work, COMMIT). Reproduced locally with a TCP proxy that delays each direction by 115 ms (not part of the repo): the "before" engine took 2.35 s to authenticate, 4.5 to 7.5 s to sign in and 5.65 s for the mentor's three-read batch, which matches the hosted numbers (hosted sign-in plus landing page 9 to 13 s). So the dominant cost is the number of sequential round trips times the Singapore to US gap; the engine pool, cold starts and per-page work are secondary. The new hosted numbers still equal the same model: about 16 round trips per mentor page (4 for authentication, 12 for the overview read).

**Quick wins made** (engine rebuilt, `check:engine` passes; measured at the simulated 230 ms round trip):

| Change | Effect |
|---|---|
| One simple query for BEGIN, search path and lock (`withCoreTransaction`) | every transaction saves 2 round trips |
| Session check and account binding in one transaction (`authenticated`) | 10 round trips to 4: authentication 2.35 s to 0.94 s |
| Sign-in binds the account and stores the session in one transaction and one statement; start-up statements in one query | login 4.5 to 7.5 s to 1.7 s (warm) |
| Pool keeps idle connections 120 s (was 20 s), keep-alive on, new `warm` engine action called while the sign-in card is shown (background thread, 90 s throttle) | the first request no longer pays to open connections; "batch after 22 s idle" 4.5 to 6.6 s became 3.77 s |
| Engine process pool in `bridge.py`: two reader processes plus one agent process (planner, plan run, replay) | a plan that waits minutes for a model no longer blocks anyone's reads; one person stays on one warm reader; the model limiter stays a single limiter; offline check `verify_bridge_pool.py` (12 assertions, in CI) |
